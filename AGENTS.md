# bipe-shared: agent notes

Source of truth for registries, strings, API contract and test vectors shared by Bipe's app (bipe-app, iOS and Android), bipe-api and the site. The Element X forks (bipe-ios, bipe-android) are archived and get nothing (ADR 0155).

- Edit `registries/` and `strings/`, then run `node tools/gen.mjs` and `node tools/gen-test-vectors.mjs`. Never hand-edit generated Swift or Kotlin.
- Registry entries must already be normalised (`tools/lib/registries.mjs` validates and fails closed).
- Regexes must stay portable: ICU (Swift), java.util.regex (Kotlin), V8 (Node 24). Fixed-length lookbehind only; `(?i:...)` modifiers are fine.
- `tools/lib/registries.mjs` `normalize()` is the reference implementation. Platform code must match `test-vectors/normalization.json`.
- Generate, never copy (ADR 0031): a rule more than one surface uses lives in `registries/` and reaches Swift, Kotlin and the API through `tools/gen.mjs`.
- A route that takes no access token has `security: []` and an `x-summary-pt` in `api/openapi.yaml`. bipe-web lists every such route on `/docs/links/` from `tools/lib/public-routes.mjs`, so a new public route reaches the docs with no edit there. `tools/public-routes.test.mjs` fails on a route whose description starts "No auth" or "Public" without the marker.
- After a contract change, run `node tools/check-contract.mjs`. After a registry or vector change, the bipe-app suites run the vectors in CI (`ios/BipeKit/Tests/BipeKitTests/SharedVectorTests.swift`, `android/libraries/bipe/src/test/.../SharedVectorTest.kt`).
- A string, registry or product change is done only when `node tools/check-drift.mjs` passes: regenerate, then commit the generated files in every sibling repo. The pre-commit hook runs it (`git config core.hooksPath .githooks`).
- The pre-commit and pre-push hooks check the sibling checkouts next to this repo (`../bipe`, `../bipe-app`, `../bipe-api`, ...) as they are on disk. Before you commit, fetch them and check out each sibling's branch of the same name (or `main`). A stale sibling, or one on another branch, fails the hook with drift that your change did not cause. To check without a checkout, export each tree into one folder (`git archive <ref> | tar -x -C <dir>/<repo>`) and run `node tools/check-drift.mjs --repos <dir>` and `node tools/parity.mjs --repos <dir>`.
- Sibling CI (bipe-app tests, bipe-web build) uses the bipe-shared branch of the same name when it exists, also after that pull request merged. A stale branch of that name makes the sibling test old vectors (bipe-android#51 failed on a missing `test-vectors/cleared-chats.json`). Merge `main` into the stale branch, or rename the sibling branch.
- Every change to `main` goes through a pull request; a ruleset blocks direct pushes. On a pull request, the `regen` job in `.github/workflows/checks.yml` pushes the generated files to a branch of the same name in bipe, bipe-api and bipe-app and opens a "Regenerate from bipe-shared" pull request there. After the merge, the `land` job turns on auto-merge for those pull requests. Do not open them by hand. A sibling branch of the same name that you made yourself gets the generated commit on top.
- A sibling pull request on that branch must have `main` as its base. `land` merges only pull requests based on `main` and warns about the others. A stacked pull request (base: another feature branch) merges into that branch, and main misses the change and its generated files (bipe-ios#92, bipe-android#82 on 21 Oct 2026). Retarget it to `main` before the bipe-shared merge.
- Regen output covers only its own branch. When you merge several bipe-shared pull requests one after another, each regen misses the others, and the drift check on `main` fails. Merge one, wait until its sibling pull requests land and `main` is green, then update the next branch with `main` (`gh pr update-branch`) so that its regen runs again.
- Push order: push bipe-shared first, then the siblings. Sibling CI and `regen` read the bipe-shared branch of the same name when the job starts. A sibling pushed before bipe-shared tests old vectors (Android `FileNotFoundException` or `NoSuchElementException` in `SharedVectorTest`). `regen` can also race your own sibling push and fail with "fetch first", or fail when a sibling branch was deleted. Re-run the failed job; do not change code.
- Merge order turns bipe-app `main` red for a short time. The app pull request merges before its bipe-shared pull request, so app `main` runs its vector tests against bipe-shared `main`, which does not have the new vectors yet (on 31 Oct 2026, `govbr-verify.json` missing after bipe-app#83 and #544). After the bipe-shared merge, re-run the failed jobs on app `main` (`gh run rerun <id> --failed`). Do not revert the app merge.
- `tools/gen.mjs` writes into `../bipe-app`, Bipe's app (bipe-chat/bipe#550): `ios/BipeKit` and `android/libraries/bipe` (Kotlin package `chat.bipe.shared.generated`, module namespace `chat.bipe.shared`), plus `BipeScreen` from `product/screens/`. Every file there carries the app store permission header (ADR 0144). The generator fails when an Element name would reach bipe-app (clean room, ADR 0143).
- `design/tokens.json` holds the colour tokens of bipe-app (bipe-chat/bipe#551, `design/README.md`). Never hand-edit its `ramps`: run `node design/ramps/ramp.mjs --write`. bipe-web reads them too: its `vite.config.ts` writes `.generated/colors.css` from this file (`generateColors("css")`).
- No npm dependencies. Node built-ins only.
- Write docs in ASD-STE100 style. pt-BR strings follow `../bipe/docs/design/linguagem.md` (ADR 0039). UI strings are draft until they pass the humanizer.
- `product/version.json` is the version line of the archived fork app (ADR 0088, ADR 0163). bipe-app has its own `version.json`; its store tools check that a new build number is above this one. Change it only with `node tools/bump-build.mjs`.
- `product/product.json` (promise, tentpoles, features) and `product/distribution.json` (download links) feed bipe-web and `bipe/docs/product.md`. After a change, run `node tools/gen-product-doc.mjs`; it validates and fails closed. A feature has no status in `product.json`: its status per surface is the `parity.json` item with the same id (bipe-chat/bipe#300). Status per surface: `testing` only when it is in a tester build; `built` when the code is merged on that surface but not in a tester build; else `planned` (or `policy`, or `n/a` with a reason). Set `built` in the same change that merges the feature (ADR 0031).
- Every feature page shows an in-app mockup (a scene or a sim). A planned feature gets one too, labelled as a simulation with the planned status. Every feature in `product/product.json` has `figures` (scene or sim ids from `../bipe-web/src/sim/scenes.ts`); `node tools/gen-product-doc.mjs` fails with "figures required (a mockup of the app)" otherwise. Add the scene in bipe-web before the feature. The `regen` job checks `figures` against bipe-web `main`, not the bipe-web branch of the same name, so a feature PR with a new scene fails `regen` ("unknown figure") until the scene is on bipe-web `main`. When the scene uses a new cast entry, merge in three steps: (1) a bipe-shared PR with only the `cast.json` entry, (2) the bipe-web scene PR, (3) the bipe-shared feature PR, after `gh pr update-branch` (bipe-shared#205, bipe-web#38, bipe-shared#204).
- `product/parity.json` is the parity ledger (ADR 0092): status per capability on iOS, Android, web and server, with evidence paths. A change that merges a capability on one surface sets its status there, with evidence, in the same change. A gap between the apps names its open issue: CI runs `node tools/parity.mjs --issues`, which fails when that issue is closed or missing (M2 exit test). A behaviour difference between the apps goes in `differences`. `ios` and `android` are bipe-app: a bipe-app PR that merges a capability sets them to built with evidence under `bipe-app/ios/` and `bipe-app/android/` in a bipe-shared PR. An item with `fork: true` is one the archived fork app ships: until bipe-app replaces it in the stores, it stays built or testing on both apps, planned with its open issue, or n/a with the excluding ADR. `node tools/parity.mjs` must pass.
- `product/data.json` is the LGPD record of processing (ADR 0090) and feeds `/lgpd/` on bipe-web. A new table, log or third-party service that holds personal data gets an item in the same change. List only what runs today. `node tools/gen-product-doc.mjs` validates it.
- `product/appstore.md` is the store listing for the App Store and Google Play (bipe-chat/bipe#453). Tools parse it with `tools/lib/appstore.mjs`; do not copy its text elsewhere. After a change, run `node tools/check-appstore.mjs`. Store text is Bipe voice and passes the humanizer.
- `product/store-captures.json` is the sample data of the bipe-app store captures (bipe-chat/bipe#457): one entry per slug of the appstore.md screenshot table, with cast ids only (a message's `image` names a cast photo, its `sticker` a file of bipe-web `src/cast/stickers`). `tools/gen.mjs` writes it into bipe-app `android/app/src/screenshotTest/.../store/generated/StoreCaptures.kt`, with the scam warning of each message from `scamWarningKind` and the BR Code from `buildBrCode`. bipe-app `tools/store-captures-ios.mjs` reads the file as it is for the iOS captures; a new key there needs the iOS reader too. `node tools/check-appstore.mjs` checks it and lists the slugs with no capture source yet.
- `product/cast.json` is the fictional sample cast (bipe#454): the site simulations (bipe-web `src/cast/`) read it. Style rules and photos stay in bipe-web (`src/cast/STYLE.md`, `src/cast/photos/`). Never rename an id that a scene or a store screen uses.
- `product/privacy.json` is who can read what (ADR 0109) and feeds `/quem-pode-ler/` on bipe-web. When a fact about message data changes (a new party such as Google push, calls confirmed encrypted), change it with `data.json` in the same change. Thing names start in lower case.

## Before you push

- CI must stay green. `scripts/verify` runs what the required checks of the `main` ruleset run. Run it before every push; the pre-push hook runs it when this clone has `git config core.hooksPath .githooks` (set it once per clone; worktrees share it).
- A push with red local checks is not allowed. Never use `git push --no-verify`.
- If CI still fails on your pull request, fix it before you start other work. Never leave a red pull request at the end of a run.

## Decisions

Product and architecture decisions for all Bipe repos are ADRs in the umbrella repo: `../bipe/docs/adr/` (index: `README.md`). Check them before changing a decided behaviour. A new decision gets an ADR there, not a note in this repo.
