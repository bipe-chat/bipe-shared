# bipe-shared: agent notes

Source of truth for registries, strings, API contract and test vectors shared by bipe-ios, bipe-android and the web console.

- Edit `registries/` and `strings/`, then run `node tools/gen.mjs` and `node tools/gen-test-vectors.mjs`. Never hand-edit generated Swift or Kotlin.
- Registry entries must already be normalised (`tools/lib/registries.mjs` validates and fails closed).
- Regexes must stay portable: ICU (Swift), java.util.regex (Kotlin), V8 (Node 24). Fixed-length lookbehind only; `(?i:...)` modifiers are fine.
- `tools/lib/registries.mjs` `normalize()` is the reference implementation. Platform code must match `test-vectors/normalization.json`.
- Generate, never copy (ADR 0031): a rule more than one surface uses lives in `registries/` and reaches Swift, Kotlin and the API through `tools/gen.mjs`.
- After a contract change, run `node tools/check-contract.mjs`. After a registry or vector change, run `swift test` in `../bipe-ios/Components/BipeKit`.
- A string, registry or product change is done only when `node tools/check-drift.mjs` passes: regenerate, then commit the generated files in every sibling repo. The pre-commit hook runs it (`git config core.hooksPath .githooks`).
- The pre-commit and pre-push hooks check the sibling checkouts next to this repo (`../bipe`, `../bipe-ios`, ...) as they are on disk. Before you commit, fetch them and check out each sibling's branch of the same name (or `main`). A stale sibling, or one on another branch, fails the hook with drift that your change did not cause. To check without a checkout, export each tree into one folder (`git archive <ref> | tar -x -C <dir>/<repo>`) and run `node tools/check-drift.mjs --repos <dir>` and `node tools/parity.mjs --repos <dir>`.
- Sibling CI (bipe-android tests, bipe-web build) uses the bipe-shared branch of the same name when it exists, also after that pull request merged. A stale branch of that name makes the sibling test old vectors (bipe-android#51 failed on a missing `test-vectors/cleared-chats.json`). Merge `main` into the stale branch, or rename the sibling branch.
- Every change to `main` goes through a pull request; a ruleset blocks direct pushes. On a pull request, the `regen` job in `.github/workflows/checks.yml` pushes the generated files to a branch of the same name in bipe, bipe-ios, bipe-android, bipe-api and bipe-app and opens a "Regenerate from bipe-shared" pull request there. After the merge, the `land` job turns on auto-merge for those pull requests. Do not open them by hand. A sibling branch of the same name that you made yourself gets the generated commit on top.
- A sibling pull request on that branch must have `main` as its base. `land` merges only pull requests based on `main` and warns about the others. A stacked pull request (base: another feature branch) merges into that branch, and main misses the change and its generated files (bipe-ios#92, bipe-android#82 on 21 Oct 2026). Retarget it to `main` before the bipe-shared merge.
- Regen output covers only its own branch. When you merge several bipe-shared pull requests one after another, each regen misses the others, and the drift check on `main` fails. Merge one, wait until its sibling pull requests land and `main` is green, then update the next branch with `main` (`gh pr update-branch`) so that its regen runs again.
- `tools/gen.mjs` also writes into `../bipe-app`, Bipe's own client (bipe-chat/bipe#550): `ios/BipeKit` and `android/libraries/bipe` (Kotlin package `chat.bipe.shared.generated`, module namespace `chat.bipe.shared`), plus `BipeScreen` from `product/screens/`. Every file there carries the app store permission header (ADR 0144). The generator fails when an Element name would reach bipe-app (clean room, ADR 0143).
- `design/tokens.json` holds the colour tokens of bipe-app only (bipe-chat/bipe#551, `design/README.md`). Never hand-edit its `ramps`: run `node design/ramps/ramp.mjs --write`. The forks keep bipe-tokens.
- No npm dependencies. Node built-ins only.
- Write docs in ASD-STE100 style. pt-BR strings follow `../bipe/docs/design/linguagem.md` (ADR 0039). UI strings are draft until they pass the humanizer.
- `product/version.json` is the app version name and the one build number for iOS and Android (ADR 0088). Change it only with `node tools/bump-build.mjs`, once before each tester upload.
- `product/product.json` (promise, tentpoles, features) and `product/distribution.json` (download links) feed bipe-web and `bipe/docs/product.md`. After a change, run `node tools/gen-product-doc.mjs`; it validates and fails closed. A feature has no status in `product.json`: its status per surface is the `parity.json` item with the same id (bipe-chat/bipe#300). Status per surface: `testing` only when it is in a tester build; `built` when the code is merged on that surface but not in a tester build; else `planned` (or `policy`, or `n/a` with a reason). Set `built` in the same change that merges the feature (ADR 0031).
- Every feature page shows an in-app mockup (a scene or a sim). A planned feature gets one too, labelled as a simulation with the planned status. Every feature in `product/product.json` has `figures` (scene or sim ids from `../bipe-web/src/sim/scenes.ts`); `node tools/gen-product-doc.mjs` fails with "figures required (a mockup of the app)" otherwise. Add the scene in bipe-web before the feature.
- `product/parity.json` is the parity ledger (ADR 0092): status per capability on iOS, Android, web and server, with evidence paths. A change that merges a capability on one surface sets its status there, with evidence, in the same change. A gap between the apps names its open issue: CI runs `node tools/parity.mjs --issues`, which fails when that issue is closed or missing (M2 exit test). A behaviour difference between the apps goes in `differences`, then `node tools/parity.mjs --write` regenerates both `BIPE.md` tables. `ios-new` and `android-new` are Bipe Next in bipe-app (bipe#579): a bipe-app PR that merges a capability sets them to built with evidence under `bipe-app/ios/` and `bipe-app/android/` in a bipe-shared PR; every item built on an original app stays built there, planned with its open issue, or n/a with the excluding ADR. `node tools/parity.mjs` must pass.
- `product/data.json` is the LGPD record of processing (ADR 0090) and feeds `/lgpd/` on bipe-web. A new table, log or third-party service that holds personal data gets an item in the same change. List only what runs today. `node tools/gen-product-doc.mjs` validates it.
- `product/appstore.md` is the store listing for the App Store and Google Play (bipe-chat/bipe#453). Tools parse it with `tools/lib/appstore.mjs`; do not copy its text elsewhere. After a change, run `node tools/check-appstore.mjs`. Store text is Bipe voice and passes the humanizer.
- `product/cast.json` is the fictional sample cast (bipe#454): the site simulations (bipe-web `src/cast/`) and the iOS store screenshots (`BipeCast.swift`, generated by `tools/gen.mjs`) read it. Style rules and photos stay in bipe-web (`src/cast/STYLE.md`, `src/cast/photos/`). Never rename an id that a scene or a store screen uses.
- `product/privacy.json` is who can read what (ADR 0109) and feeds `/quem-pode-ler/` on bipe-web. When a fact about message data changes (a new party such as Google push, calls confirmed encrypted), change it with `data.json` in the same change. Thing names start in lower case.

## Before you push

- CI must stay green. `scripts/verify` runs what the required checks of the `main` ruleset run. Run it before every push; the pre-push hook runs it when this clone has `git config core.hooksPath .githooks` (set it once per clone; worktrees share it).
- A push with red local checks is not allowed. Never use `git push --no-verify`.
- If CI still fails on your pull request, fix it before you start other work. Never leave a red pull request at the end of a run.

## Decisions

Product and architecture decisions for all Bipe repos are ADRs in the umbrella repo: `../bipe/docs/adr/` (index: `README.md`). Check them before changing a decided behaviour. A new decision gets an ADR there, not a note in this repo.
